> 已定的两组见 `FREEZE-CAPABILITY-ARM.md` 与 `FREEZE-CH4-ARMS.md`。
> 本文列的是**我发现的缺口**和对应的可选臂,附成本与各自能买到什么。
> 端点现金成本约为零,故**成本单位是墙钟不是钱**;距 9/5 尚有 33 天。

## 缺口一 · E-capability 一次改了两个东西

**问题**。改造臂同时改 `--cluster-source`(容量)和 `--epsilon`(探索)。
若它与 e_pervar3 有差异,**说不出是哪一个造成的**。

**已有的部分补偿**:离线重放在**真实录得数据**上把两者分离了 ——
能力分簇单独用**更差**(基尼 0.82 vs 0.72),ε 单独用不增加容量,合用才有效。
但重放只覆盖**负载**,**准确率那一侧无法分离**。

### 可选臂 A:`E-capability-noeps`(能力分簇,ε=0)

```
--cluster-source capability --cluster-map <map>     (不加 --epsilon)
```

**成本** 约 22h。

**它买到什么**:这是**唯一有事前预测的臂** —— 重放预测它比 e_pervar3 **更差**
(容量造出来了但没有分配机制)。跑它等于检验那个预测,而不是又一次描述结果。
**预测被证伪比被证实更有信息量**,两种走向都能写。

**不跑的代价**:CH3 只能说「分簇+探索这一对起了作用」,说不出各自的份额。
对硕士论文而言可接受,但审稿人会问。

**我的倾向:值得跑。** 它是三条 CH3 臂里唯一能被证伪的。

## 缺口二 · 没有 K=1 对照,复现不了论文的 headline

**问题**。论文 Table 5 的核心主张是 **Ensemble 阻止了 Global 的退化**
(漂移 0.0 vs −24.3)。我们**没有 K=1 臂**,因此无法复现该对比 ——
这是论文最直接的机制主张,而我们整章在复现它周边的东西。

早先我判过"不该跑 K=1",理由是它要对照的 s1k8b103 已撤回。
**该理由现在失效了**:e_pervar3 是干净的。

### 可选臂 B:`E-global`(K=1,其余同 e_pervar3)

```
--pool-k 1     (其余旗标与 e_pervar3 完全一致)
```

**成本** 约 22h,可能更短(单变体,无 fork,无候选门的多目标开销)。

**它买到什么**:论文 headline 机制主张的直接复现。
`e_pervar3 − E-global` 的漂移差,就是 Table 5 的 `Ensemble − Global` 那一格。

**⚠️ 必须带去偏读**:两臂的 `终−峰` 都含 max-of-N 偏置(n=16 时约 8.1pp)。
论文报的 −24.3 也含同样的偏置,**但论文没做这个修正**。
故我们的对比要报两个版本:原始差值,以及去偏后的差值。
**「论文的 Final−Peak 指标在构造上向下偏」这一条,只有跑了 K=1 才有实测支撑** ——
否则它只是一个算术论证。

**我的倾向:这条比缺口一更值得跑。** 它把 CH3 从"我们改进了复现"
提升到"我们复现并检验了论文的核心机制主张"。

## 缺口三 · 归因每轮被算出又被扔掉(**夜间新发现,我认为这条最有意思**)

**事实**(实测,非推测)。LLM Digester **每轮都产出真实的组件级归因** ——
`tools/Bash`、`processor/TokenBudgetProcessor`、`tools/WebFetch`、`model_capability` ——
覆盖 e_pervar3 R1 的 30/103,s1k8b103 逐轮 20–80%。

**但它不跨轮传递。** 交给下一轮的 `prior_history` 条目形如:

```
{round_idx, variant_id, outcome, solved, failure_category: null, ships}
```

`failure_category` 为 null,`implicated_components` **这个字段根本不在**。

原因是两处,都很具体:
1. **持久化的 digest 是确定性版本**(`failure_category = gaia_level_N`),
   不是 LLM Digester 的富化版本
2. `EvidenceStore.cross_round_history()` 构造条目时**没有把 `implicated_components` 放进去**

**后果**。演化器看得到「这题**这一轮**栽在 Bash 上」,
**永远看不到「它连续五轮都栽在 Bash 上」** —— 而后者才是定向演化需要的形式。

论文 §4.3 p.10 自己说这段历史的用途是让 Planner
*"distinguish persistent failures from transient noise"* ——
**没有归因的历史做不到这件事。**

**佐证**:e_pervar3 的 R1 短路于 `planner_empty_landscape`,
Planner 自述理由正是「**没有前轮可比**」。

### 可选臂 C:`E-attrib`(归因持久化)

改动:把 LLM Digester 的 `failure_category` 与 `implicated_components`
写进持久化 digest,并让 `cross_round_history` 带上它们。旗标化,默认关。

**成本** 约 22h + 小改动。

**它买到什么**:这是**唯一由我们自己的诊断推导出来、且论文文本明确要求其功能的修复**。
论文说这段历史是为了区分持续失败与瞬时噪声;我们实测它做不到;我们修好并测效果。
比"换个分簇维度"更贴近论文自身的机制主张。

**风险**:它改的是演化循环的输入,是个新变量,不能和改造臂混在一条里。

**我的倾向:优先级排在缺口一(K=1)之后、缺口二之前。**
它便宜、有论文原文支撑、而且是今晚唯一一条**"信号被算出来又扔掉"**型的缺陷 ——
修复成本远低于其它任何改进。
