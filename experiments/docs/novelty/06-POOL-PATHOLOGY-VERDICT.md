> 2026-08-03 定稿。**本文覆盖 `01-CANDIDATES.md` 与 `04-PROBE-RESULTS.md` 中关于这三条的一切表述**——那两份里的旧机理已被推翻，见 §4。

## 0. 三条定案

| | 定案 | 一句话 |

| **N-10** | ✅ **成立，值得修** | 病理是**时序错配**：目标在路由冻结**之前**选定，冻结随即把目标的题判给同簇更强的兄弟，目标承载归 0，管线跳过 ⇒ 整轮零候选。s1k8b103 上 6/15 轮 |

## 1. N-10 — 目标选择与路由冻结的时序错配

### 1.1 机理

```
recipe:4260   选目标        ← eligible 用【上一轮】的 routed_tasks（recipe:4321-4326，要求非空）
                              worst_first = min(variant_ids, key=ledger.variant_rollup)  (target.py:89)
      ↓
engine:297    路由冻结       ← 本轮按 argmax 重算
engine:300    apply         ← 目标的题被判给同簇更强的兄弟
      ↓
engine:316-319 跳过空簇变体  ⇒ 零候选，整轮空转
```

**目标不是"长期僵尸"，是"刚被夺食"**：6/6 废轮的目标在**上一轮都还带着题**（主循环用独立的 routing dump 核过）：

```
R3  目标V1 ← R2 时 V1=64      R5  目标V2 ← R4 时 V2=21      R8  目标V4 ← R7 时 V4=12
R9  目标V5 ← R8 时 V5=12      R12 目标V4 ← R11 时 V4=10     R14 目标V6 ← R13 时 V6=61
```

### 1.2 关键否证：不是"无数据→0.5→排最差"

6 个废轮目标的 rollup 分数是**真·低分**，无一走冷启动路径：

```
R3 V1=0.48   R5 V2=0.15   R8 V4=0.38   R9 V5=0.11   R12 V4=0.25   R14 V6=0.49
```

（`variant_rollup` 默认 `task_macro`，`ledger.py:319-320`；仅当变体无任何 cell 才回退 `stale_prior=0.5`，`ledger.py:311-312`→`258-263`。选目标处 `recipe:4260` 用全累积 rollup，无 `before_round` 裁剪。）

⚠️ **收益上界不是 6 次上线**：R10/R15 证明"有题 ≠ 会上线"（有题也被门拒）。上界是"6 轮从零候选变为有候选可尝试"。

### 1.4 爆炸半径极小

`_paper_target_variant` 功能上**只被 `recipe:4358` 消费**（`_evolve` 对非目标 return None）；其余仅写入快照/报表（`recipe:5680,5818`）。**不参与结算、归因、退役、路由。**

### 1.5 "排除" vs "退役"：退役是错的，且退役救不了这个病

- 退役救不了：目标是**刚被夺食**的，不是长期空载，退役规则根本抓不到它。
- 退役还会误杀：**承载 0 ≠ 死**。休眠变体会复活——V5 在 R9/R10 连续零承载，**R11 拿走 52 道题**；V1（R3→R4）、V4（R8→R9）、V6（R14→R15）同样复活过。任何"连续 N 轮零承载即退役"都会误杀它们。
- 退役的连带面也大得多：弹出 `pool.variants`（降 `variant_count`）、产生 orphan 需 `reassign` 重路由（`engine:559-565`）、剪掉缓存 meta-agent、写 `fork_retire_events`（`reporting.py:456`）；但**不删** ledger cell（`pool.py:218` 保 `ever_solved`）、**不删** `learnings_V*.md`。

⇒ **修法只能动目标选择的时序，不要碰退役。**

### 1.6 复现范围（论文里必须如实写）

| run | 结果 |
|---|---|

| s1k8 | 单变体、0 fork、**0 个废轮** |

⇒ **N-10 是"多变体 + 足够轮数"才显现的现象**，机理通用但只在旗舰床爆发。不可写成普遍规律。

## 2. N-06 — 毙掉

### 2.1 真相是第三种情况：写了，但盖了时间戳，迟到一轮

前提：`candidate_mode="paper"` ⇒ `record_selected_results=False`（`recipe:4212`），三床均确认。故：

1. fork-settle 的 `engine:594` 守卫为假 ⇒ `_record(child, tk_eval)`（595→735-738）**不执行**；
2. 但同一批测量（**仅 improved 子集**）经 **candidate_reuse**（`recipe:5335-5341`，`_safe_candidate_reuse:5441` 从 `result.per_variant_pass` 取值）→ `_record_settled_active_outcomes:5410` **写进 child 的 ledger**，`round_idx = fork 轮`；
3. 而 `estimate` 用 `before_round = fork轮`，**结构性排除本轮** ⇒ fork 当轮该 child 预测 = 0.5（`ledger.py:261-262`），**下一轮起才可见 ~0.70**。

### 2.2 为什么零后果

**那个 0.5 从不被任何决策消费**：child 在 fork 轮的**冻结之后**才诞生，本轮的路由与退役都不含它；到下一轮 ledger 里已有它的真实数据。

**数据佐证**：每个新生变体在 fork 后一轮**承载量全部增长**（V1:21→64、V6:2→64…），**无一因低估被饿死**。真正被饿死的是被它们顶替掉的老变体——那是 N-10 的受害者。

⇒ **N-06 与 N-10 基本独立，且不喂养 N-10。**

### 2.3 强行修的两个坑

- **双计（已证）**：child 的 candidate_reuse cell 与 candidate_gate cell 在共享（improved）题上**逐值相等且 child ⊆ gate**（7/7 fork）。加"fork 时转入 gate 测量"会在**同一 round_idx** 双计（`ledger.record` 累加 passes/attempts）。防双计位置：`recipe._safe_candidate_reuse:5441` / `_record_settled_active_outcomes:5398`。
- **oracle 污染**：若为救标定把 fork 轮数据前移到 `fork-1`，会**泄漏进 fork 轮的路由冻结**。

### 2.4 冷启动与数据量（备查）

- `estimate_cluster`（`ledger.py:170-196`）→ `aggregate_counts` → `_rate`：`attempts==0` 返回 `stale_prior`(0.5)；否则 Laplace **一次性加在簇聚合** `(Σpass+1)/(Σatt+2)`（`ledger.py:182-184`、`261-262`），**非逐题**。
- `candidate_gate_measurements` 按**父目标**键、覆盖父的整个 T_k：七次 fork = 103+39+52+64+52+12+64 = **386** 个 (变体,题) 对。其中**仅 improved 子集 46 个**（21+3+31+4+2+2+3）随 fork 转到 child；其余 **340 个**是候选配置在"未改进题"上的实测，child 不承载故从不记到 child 名下（真丢，但都是 child 不路由的题）。
- 低估方向**四床全复现**：s1k8b103 `0.500→0.705`、s1k8 `0.568→0.717`、a1big5 `0.665→0.842`、e_pervar3 `0.725→0.840`。

### 2.5 处置

**不改代码。** 写成一条方法学注记：*"paper 模式下新生变体在 fork 轮的路由估计恒为先验值，但该估计不被任何决策消费；下一轮起转为实测。"* 进 threats 与偏差登记即可。

## 3. N-08 — 措辞修订

### 3.1 仍然成立

**承载任务的变体数 ≤ 簇数**：非 fork 轮 ∈{2,3}，fork 当轮可到 4（= 3 簇 + 新变体的目标子集）。4 个 run 全部成立。名义 K=8 从未转化为 >3 的稳态承载多样性。

池的形态：**V0 恒守 39 道 Level-1（R4 起一动不动）；余下 64 道（L2+L3）在血脉间整体易主**（R5 归 V3、R12 归 V6、R14 归 V7）。

### 3.2 **不成立，必须收回**

- ❌ **"K=8 永远填不满"**：`variant_count` 单调 **1→8，池确实填满了**。退役不触发的真因是：`needed = max(0, active_count + len(winners) - K)`（`engine._plan_forks:615-628`），7 次 fork 时 `active_before` = 1..7，**从未在 fork 前达到 8**；池在**最后一次 fork（R13）才到 K=8**。触发退役需要"满池时又提 fork"，本 run 从未发生。
- ❌ **"僵尸 / 坟场 / 祖先永久死亡"**：**承载 0 ≠ 死，正确的词是休眠**。复活实例：V5（R9=0, R10=0 → **R11=52**）、V1（R3=0 → R4=12）、V4（R8=0 → R9=12）、V6（R14=0 → R15=12）。
  机制：路由每轮重算，休眠者的估计被冻住，但**在位者的估计会变**——在位者一退步，冻住的旧估计就可能重新成为最大值。
- 真正再没回来过的只有 V1（R4 后）、V2（R4 后）、V3（R10 后）。

### 3.3 对 N1 的影响

N1 押"**持久**演化池"。按现有数据，池是"**在位者 + 若干休眠者**"，分工不稳定但并非死的。**N1 立论前必须先确定这个前件**，或改口径。
